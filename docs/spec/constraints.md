# Constraints

Rules, limits and constants. Unlike a principle, a constraint is not weighed against anything; unlike an invariant, it is a choice that could have been different and is recorded as one.

## Technology

| Id | Constraint |
|---|---|
| **CON-1** | The harness is written in Rust, stable toolchain. |
| **CON-2** | A plugin is a crate that implements an interface trait. It is compiled into the binary of a local build and selected by name in the configuration. |
| **CON-3** | No dynamically loaded Rust libraries as plugins (Rust has no stable ABI). |
| **CON-4** | Out-of-process plugins (any language, over stdio) are not part of v1. They may be added later as another way to implement the same interfaces. |
| **CON-5** | Build targets: Linux x86_64 and arm64, macOS arm64, Windows x86_64, and `wasm32-unknown-unknown` for the browser demo. |
| **CON-6** | The terminal interface is built on ratatui. |

## Providers and authentication

| Id | Constraint |
|---|---|
| **CON-10** | v1 providers: the Anthropic API, OpenAI-compatible APIs (OpenAI, OpenRouter and the like), and local models served over an OpenAI-compatible endpoint. |
| **CON-11** | Shipped `Auth` implementations: API keys (from the environment, the config, or the OS keychain on native targets) and `gpt-subscription` (CON-55). See INV-9 for what is not shipped. |

## Memory and sessions

| Id | Constraint |
|---|---|
| **CON-20** | The default `Memory` implementation is a local daemon that owns a project journal (entries with categories, tags, flags and links, lexical search, CON-119), mind maps and flowcharts. The same daemon is the single entry point of callbacks to agents, with a callback URL for every open agent window (IF-13). In the browser, the same interface is implemented over browser storage. |
| **CON-21** | Journal flags include work items (todo, question, problem, bugreport, reminder, unverified, disputed) and marks (specification, constraint, important, idea, concept, comment, verified, deprecated); an entry carries any number of them. |
| **CON-22** | One journal per project; a project is identified by its repository remote, or its directory when it has none. |
| **CON-23** | Callback triggers (IF-13) are configuration of the project, versioned with it; every callback names its `type` (IF-13), and the harness types are `notification` (a callback delivered into the agent's input, its stdin — the inbound CALLBACK card the TUI shows; `/callback` publishes one), `journal` (only writes a journal entry from the event; no agent turn), `flowstate_update` (changes the state of one instance of a flowchart — a pass keyed by the client's pipeline id, never the reference chart; no agent turn) and `skill` (starts a run of a named skill with the event as input; kept as a concept, may be dropped); product types are any string, with custom handlers (IF-16); a flowchart's binding to a process and to its watching sessions is configuration too. A callback whose type has no handler reaches no agent: it is logged and the caller gets 400 (ADR 0015). Neither a `journal` nor a `flowstate_update` callback starts a model turn. |
| **CON-24** | Step-debug runs are stored in the target project, in an SQLite database under `.harness/debug/`: one run per cycle, saved when the run reaches a terminal block of its flowchart. |
| **CON-25** | Step-debug code in a target project (debug router, step waits, the mode's callbacks) is active strictly behind the environment gate `MULTITOOL_DEBUG_MODE=1` and only with authorization — checked by the app itself or by a token issued by the harness daemon; without the gate the code is inert and the pipeline runs as uninstrumented ([ADR 0013](../decisions/0013-step-debug-mode.md)). |
| **CON-26** | A project's response policies (reliability monitoring) are Markdown files under `.harness/policies/` in the project; conditions link their paths ([ADR 0014](../decisions/0014-reliability-monitoring-mode.md)). |
| **CON-27** | The step-debug router of a target app is always built by one contract, an OpenAPI-style specification the harness ships: an `approve` route that lets the app go to its next step; a `step back` route only where stepping back is really possible — otherwise not implemented at all, no stubs; the app's other product routes as the product needs ([ADR 0013](../decisions/0013-step-debug-mode.md)). |
| **CON-28** | A debug-router route for debugging product behaviour or invariants imports and calls the functions the real code calls; it implements no business logic of its own. A route that reimplements logic instead of calling the code it debugs breaks the contract ([ADR 0013](../decisions/0013-step-debug-mode.md)). |
| **CON-29** | A step-debug pipeline waiting after a callback advances only on the agent's `approve`: no timeout, no default action, nothing on its own if the agent or its session is gone ([ADR 0013](../decisions/0013-step-debug-mode.md)). |

## Browser build

| Id | Constraint |
|---|---|
| **CON-30** | The browser build has no shell, no processes and no daemon: files live in an in-memory or origin-private file system, network goes through `fetch`, storage through IndexedDB. |
| **CON-31** | The user's key in the browser build is entered by the user and stored only in that browser. |

## Project

| Id | Constraint |
|---|---|
| **CON-40** | The repository is self-contained: it does not refer to, depend on or name the project it grew out of. |
| **CON-41** | Every spec item, invariant and constraint has a stable id; ids are never reused. |
| **CON-42** | A change to a principle, invariant, constraint or interface contract goes through a decision record in `docs/decisions/`. |
| **CON-43** | Once a project has its docs tree (created by the `project-init` skill), its journal, mind maps and flowcharts are mirrored into Markdown files in its repository — README, architecture, spec (principles, interfaces, invariants, constraints, open questions, roadmap), decisions, flowchart pages — and kept consistent with them in the same change; the agent writes the files, prompted by a `PostToolUse` hook on every memory write; a disagreement is a finding settled before work goes on ([ADR 0017](../decisions/0017-docs-mirror-memory.md)). |
| **CON-44** | Project initialization (`project-init`) creates the docs tree and the `.harness/` folder; it never overwrites an existing file. Everything in `.harness/` is committed with the project, for now. The harness asks about it once, at the first start in a project without `docs/` and `.harness/` ([ADR 0017](../decisions/0017-docs-mirror-memory.md)). |
| **CON-45** | The docs-mirror check is advisory and structural: a built-in hook plugin on typed memory-write events, linked by doc id (the file named by the category contains the id; settled and deprecated items are marked); a `Stop` hook adds one reminder per turn and never vetoes, forces continuation or loops; the same checker runs as `multitool docs check` and in CI. It does not judge whether the prose agrees ([ADR 0017](../decisions/0017-docs-mirror-memory.md)). |
| **CON-46** | The documentation files are a storefront: only the current, settled state, written to be read. No drafts, work notes, scratch text, TODO placeholders, half-written sections, superseded variants kept for history, or assumptions written as facts; work in progress lives in the journal, maps and charts, history in git. What is not settled appears only in its declared form: an open question, an ADR with status `proposed` or `concept`, a labelled proposal ([ADR 0017](../decisions/0017-docs-mirror-memory.md)). |

## Plugins and callbacks

| Id | Constraint |
|---|---|
| **CON-50** | A hot reload swaps the binary only at a safe point — no model turn streaming, no tool call in flight — and never loses the view: everything held only in memory goes to a hand-off file the new process restores; a failed build swaps nothing ([ADR 0015](../decisions/0015-callback-handlers-are-plugins.md)). |
| **CON-51** | A project's `.harness/acceptance.toml` runs only in the exact text the user approved; any change, by anyone, asks again. Commands the user gives for a task need no approval. Commands in journal entries never run. |
| **CON-52** | The Telegram channel delivers only messages from `allowed_users`, as data marked external (INV-12) under a label a callback cannot claim. Its token is the harness's own, and appears in no log, status or error. No token means nothing polls. A reply goes to the chat of the last allowed message and asks permission first. An empty list delivers nothing; anyone else is dropped and counted, their text never logged or stored; the list changes only in the configuration file, never through the channel. `telegram_send` asks permission like any outward action, sends only to the chat of the last allowed message or the configured chat, splits text over 4096 characters, and answers an error when neither chat is known. |
| **CON-53** | In plan mode the engine refuses writes and every command but a single known read-only one, before hooks and policy, so no answer can approve them ([ADR 0016](../decisions/0016-plan-mode.md)). The exception is writing under `docs/` (CON-65). Only the user ends the mode. The read-only commands are: one command, no shell operators, redirection or substitution; `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `pwd`, `stat`, `du`, `df`, `git status/log/diff/show/blame`. Options that write or run something (`--output`, `--pre`, `--ext-diff`) are refused, and anything unknown is, so the list fails closed. These still ask permission under the policy. |
| **CON-54** | A permission prompt takes only Deny for its first 800 ms on screen: it can open at any moment, started by a callback or a channel, and keys meant for the composer must not approve it. |
| **CON-55** | A ChatGPT plan is reached only by OpenAI's documented flow for open-source apps: the harness registers a client of its own, the user signs in on OpenAI's page, the ID token and the plan scope are validated before anything is saved, tokens are owner-only and in no log, and requests go to `POST /v1/responses` with `store` false and `stream` true. |
| **CON-56** | Claude subscription credentials are not supported: Anthropic does not permit third-party apps to offer Claude.ai login or to collect, store or route its tokens ([its terms](https://code.claude.com/docs/en/legal-and-compliance)). The `claude-subscription` adapter exists only to refuse: it holds no token logic, the settings list it and answer with a toast. Anthropic models take a Console API key or a cloud provider. |
| **CON-57** | The Claude Code delegate runs the unmodified `claude` binary, signed in by the user through Anthropic's own flow, and says so on screen. The harness never reads, stores or passes its credentials, and neither replaces its system prompt nor its tools. It is behind a cargo feature, off by default, until Anthropic answers ([ADR 0020](../decisions/0020-claude-code-delegate.md)). |
| **CON-58** | Delegate mode `oneshot`: `claude -p` with stream-json per message, the prompt on stdin, `--resume` with the stored session id. Nothing runs between messages. |
| **CON-59** | Delegate mode `session`: one process per tab with stream-json on stdin. It ends after 10 idle minutes and at a hot reload, and comes back with `--resume`. A process that dies mid-run is an error card; the session stays. |
| **CON-60** | A delegate's tool that would prompt goes to the harness's own prompt; no answer is a denial. A task's `Verifier` still decides done. Its limits reach the user and are not retried in a loop. On a subscription its cost shows as included and charges no budget. |
| **CON-61** | By default the nested `claude` runs only the harness's MCP configuration and no user hooks, if the flags keep the login; otherwise the delegate says on screen what it inherits. CON-69 is the opt-in exception. |
| **CON-62** | Building an app, a prototype or a project, a feature, a fix or any change that is not trivial starts in plan mode, even if nobody said plan; nothing is built before the plan is approved ([ADR 0021](../decisions/0021-agent-behaviour.md)). Answers, reading, diagnosis and work in an approved plan are exempt. |
| **CON-63** | A planned fix goes on in debug mode, reproduced before it is changed and verified after; a planned feature is built and run, then debugged in debug mode the same way; only a pipeline gets a router and instrumentation. Work ends with evidence in the journal. |
| **CON-64** | The behaviour rules are in every session's system prompt. The hook `mode-guide` acts on the first write in a message with no plan made in the session: `plan_first` is `remind`, `enforce` or `off`. It never touches reads or memory and cannot loop. |
| **CON-65** | While planning, a path under the project's `docs/` may be written; a path that climbs out of it may not. Every other write stays refused ([ADR 0021](../decisions/0021-agent-behaviour.md)). |
| **CON-66** | `mode-guide` says the step of the cycle that is due, for one turn: at each user message and at each change of mode. A `plan_exit` with no journal entry, map or flowchart goes back once, or under `enforce` until they exist. Stopping after an approved plan or in debug mode continues the run once per message. |
| **CON-67** | `ask_user` shows a question with up to 9 options and ends the run; the answer is the user's next message: a chosen label or their own words. A message queued meanwhile is that answer. Each option is a label with an optional description; the panel above the composer takes Up/Down and Enter or a digit, and typed text answers instead. |
| **CON-68** | The same call failing the same way within one user message gets a reminder the third time and ends the run with a visible error the fifth. A new message starts the count over. |
| **CON-69** | A delegate row with `environment = "user"` runs `claude` with the user's own settings, hooks, servers and environment; only the markers of a running session are removed. Opt-in ([ADR 0022](../decisions/0022-claude-code-conversations.md)). |
| **CON-70** | A delegate row with `permissions = "skip"` runs with no permission prompts. It is only ever the user's own setting: the harness never turns it on, and no answer or message can. |
| **CON-71** | What the harness adds to a provider's form is only ever appended, on the form's own chain: every byte already there stays as it was. A conversation goes on under its own id, with no fork ([ADR 0025](../decisions/0025-one-conversation-in-every-form.md)). |
| **CON-72** | An import keeps each tool result to 4 KiB and no images: the whole stays in the source's own record. Lines it cannot read are counted and passed over; a rewound branch or a subagent's lines are not part of the conversation. |
| **CON-73** | The harness's event log is the conversation. Any provider can go on with any session: what it is sent is valid for it whatever made the log, with roles alternating and every call answered, and what a provider signs for itself goes to no other ([ADR 0023](../decisions/0023-the-log-is-the-conversation.md)). |
| **CON-74** | A session that goes on through a provider keeping its own conversations and has no form there is written in that provider's form first, as a new one, and is linked to it. A linked form stays current through any other provider's turns. |
| **CON-75** | A conversation runs in the daemon, which alone writes its log. A frontend is a client. Only a scripted run, `multitool run`, and a window with no daemon to be had run a session themselves ([ADR 0024](../decisions/0024-conversations-live-in-the-daemon.md)). |
| **CON-76** | A window that goes away leaves its runs to finish in the daemon, and a prompt nobody can answer is a denial. A window that has not polled for 30 seconds is gone. |
| **CON-77** | One writer to a log: a session open in a window still there does not open in another, and the window says so. From a window that went away (silent for 5 seconds) the session comes to the one opening it, with its run if one is on. |
| **CON-78** | One writer to a form: while the provider's own program has a conversation open, the harness reads it but refuses to send, naming the program. Which program holds what is read from the provider's own record of its running sessions. The harness cannot stop that program from opening a conversation in the middle of a harness run: not doing so is the user's part. |
| **CON-79** | Changing the adapter or model is done in the harness's settings and saved by the harness; no file needs editing. It reconnects the active tab's conversation at once (CON-94), and the daemon brings its form for that adapter in line, creating it if there is none. While any of them has a run on or a prompt waiting, the controls are disabled and say why, and the daemon refuses such a change. |
| **CON-80** | The context window is chosen from a dropdown in the settings, per provider, and saved by the harness. Auto takes what the server or the model reports; a chosen value wins over a report, and compaction goes by it. |
| **CON-81** | While the daemon brings a form in line or reads one (on a change of adapter, or on opening a conversation), the window shows the moon-phase spinner and takes no input, until the daemon signals success or failure. The daemon's work does not hold up its other windows. Replaced in part by CON-136: only the conversation being brought in line is held, never the whole window. |
| **CON-82** | With no session to deliver to, a Telegram message goes to the window that most recently polled the daemon within the last 60 s, which starts one. With none, the update stays unconfirmed so it is not lost. After delivery the offset advances and is stored, so a restart does not repeat it. Flood control's `retry_after` is respected. |
| **CON-83** | A message sent during a run is shown above the composer and reaches the model at the next boundary, after the tool results before it, in order and once; its card appears then. If the run ends first it starts the next one. Up on an empty composer takes the last back, and it is never delivered. Esc stops, and the queue then runs at once. A rebind keeps the queue, tabs keep theirs apart, and a task's message waits its turn. |
| **CON-84** | What an agent backend runs in the background shows above the composer while it runs: a moon, what it is, for how long, at most three and the rest counted, and a card with its summary when it ends. Between runs the backend's stream is still read: a turn it begins by itself is a run like any other, shown at once, taking messages, and a reload waits for it. A result that came before a run's own prompt came back does not end that run. A log read back shows no task on, since the process that held them is gone. |
| **CON-85** | `multitool debug screenshot` draws the open window as it is now, overlays included, into a PNG the caller names, with the renderer of `multitool screen`, and waits up to 10 s for it. It shows the harness's own state only, never the desktop. |
| **CON-86** | In a session, Ctrl+C stops the run in the active tab, as Esc does, and what is queued goes to the agent at once; a second press cancels that answer too, and what was queued reaches the agent with the next message. With no run on, the first press says `Ctrl+C again to quit` and a second within 2 s quits. On the splash and start pages it quits at once. `/exit` always quits. |
| **CON-87** | One bot token serves any number of sessions. A chat, or a forum topic, is bound to one session, in a file of the daemon's that survives a restart; one session holds one binding, and a new bind moves it. `/agents` and `/start` list the open sessions with buttons, `/switch` with a number or words of a title binds, `/whoami` says what is bound; these reach no session, and unknown commands do. A message goes straight to the bound session. Unbound with one session open, it binds to that and says so. Unbound with several, or bound to one not open, it is held, the sender is told and offered the buttons, and it goes on when one is chosen; never dropped in silence, at most 20 per chat. `telegram_send` from a session goes to its binding. `/id` answers anyone with their own user id and nothing else, keeps nothing and reaches no session, so one can learn it before being allowed. Another poller on the token is named as the error. The token and the allowed users are set on the settings page, which never shows a saved token, and saving restarts the channel at once. |
| **CON-88** | A session registers with the daemon by being open, and goes by a nick set with `/nick` in its window, by the agent itself, or with `/nick` in its bound chat. The daemon keeps the nicks across restarts. `/switch` finds a session by number, by exact nick, or by words of its title. A binding follows the session, not the nick. |
| **CON-89** | Speech to text is chosen and installed in the settings, section Speech to text: an engine (whisper or parakeet), a model of it, a download fetching a runtime and the model on the user's word, and a test from the microphone that shows the level and the words. Nothing else fetches them, and nothing is built in. An allowed Telegram user's voice note is transcribed on this machine and reaches its bound session as a voice message. With no engine set up, the user is told, in the window and in the chat, and the agent is not: it is the user's to set up. A stranger's note is never fetched. Any other failure, or a message neither text nor voice, is told to the sender. Transcribing holds up no other chat. |
| **CON-90** | `install.sh` and `install.ps1` build from source, from a checkout with `--local` or a temporary clone, and put the binary on the PATH. They install no speech engine, which is the settings' (CON-89). Build dependencies are named with the exact command and installed only on the user's word. They touch no shell profile. `--uninstall` removes the binary and keeps the user's data. |
| **CON-91** | A journal entry can be blocked by another: while that one is not closed, the blocked one cannot be closed, nor a todo whose branch holds it. An agent that meets a problem which cannot be solved until another in the journal is solved sets this, and works on the blocker first; it says so in the tool's own description. Abandoning is not refused, since dropped work waits for nothing. What could never close is refused when set: a cycle at any depth, itself, a blocker with nothing open, an entry with nothing to close. |
| **CON-92** | The Speech to text page chooses the input device from what the system lists when the dropdown opens, monitors left out, with Default chosen until the user says otherwise. It governs that page's test: voice notes arrive as files. |
| **CON-93** | The journal's agenda lists what waits for an open blocker apart from what can be taken now. Closing an entry answers with what that set free. A blocker abandoned instead of solved does release, and the entry that waited is listed for re-reading until the link is lifted or it closes, since what it needed is still not there. |
| **CON-94** | A conversation has its own adapter and model, kept by the daemon through reloads and restarts. The settings choose for the active tab's conversation and for conversations not started yet; other tabs and windows do not move. A change is refused only while that conversation runs or waits on a prompt. |
| **CON-95** | What a conversation does on an agent backend it does on the native loop too. A stop ends the running command and cuts the model's stream at once, with the history left valid. The shell tool can run in the background, shown above the composer, its end told to the agent. |
| **CON-96** | Harness modes are not utilities. They live under the namespace `mode__` (`mcp__mode__` on an agent backend), the system prompt says what a mode is, and every tool and mode has a description an agent can act on, all documented in [docs/tools.md](../tools.md), held by a test. |
| **CON-97** | An agent's behaviour is deterministic: a situation brings the same action every time, on every adapter, proven by a checker over the session's log. Journaling, spec-first through the journal, maps and flowcharts are mandatory. |
| **CON-98** | The agent workflow specification is part of the harness, not of a project. A hook gives the agent the path to its file at session start, after a compaction and on a resume, and it can be read with no prompt. |
| **CON-99** | Agents talk through the daemon with `agent_list` and `agent_send`, by nick or id. A message reaches the other as data from outside, with the sender's own name, which it cannot claim falsely. An agent does not message itself, and a conversation sends at most 60 in 10 minutes. |
| **CON-100** | Orchestration mode adds to the agent's prompt the tools it now has, and they exist only in the mode. The master starts agents as tabs of its group, on authorized adapters and models it chooses, in the same project and git, with the journal and all tools. A hook tells each it is a slave working for the master, explains those are only technical terms, and asks it to report ready. A slave messages only its master; the master, any of its slaves, as the user's message. A slave's `ask_user` goes to its master, not the user. In the window the group is set off together, with (M) and (S) on the titles. A slave's questions, plan and permission requests go to its master, by the user's own decision. A slave cannot spawn; at most 8. |
| **CON-101** | A journal is evidence-first unless a project turns it off: a verification must point at a proof, a kept file, log, screenshot or URL, and a todo closes only on one. A claim that something works is checked as the user will meet it. |
| **CON-102** | `/version` in the TUI displays the harness package version in a VERSION card in the current transcript, not a toast. It uses the workspace package version, is listed in `/help`, and sends no model request. |
| **CON-103** | A slave reads and writes files inside the folder it works in, runs reading commands, and builds and tests with `cargo`, with no one asked, also in chains joined by `;`, `&&`, `||` or `|`, each stage one of those, under `timeout` if it likes, with `2>&1`. Anything else goes to its master: other commands, redirection, substitution, the network, a path outside the folder. |
| **CON-104** | A new tab takes no adapter and no model from the tab it is opened from. Its ADAPTER and MODEL are its own conversation's: until its first turn it shows the default it will run on, and from then what it runs on. Opening or changing a tab never changes another tab's adapter or model. |
| **CON-105** | Isolation between tabs: opening a tab (`open_tab`) never copies or changes another tab's ADAPTER or MODEL, and the other status fields carry over unchanged, except TOKENS, COST and MODE, which a new tab resets. |
| **CON-106** | On an agent backend the plan and debug modes come over the `mode` MCP server. Leaving plan mode there takes the user's words, quoted and checked, and refuses a plan with no journal entry, mind map or flowchart. The harness cannot refuse that program's own writes: plan mode holds from its next message. |
| **CON-107** | `/tabs` in the TUI publishes a TABS card in the current transcript: one row per open tab, in order, with its number, title, and its own ADAPTER and MODEL (a dash when none is set), the active tab marked. It is local and read-only: no tab changes, no daemon call, no model request. |
| **CON-108** | A slave on an agent backend always runs isolated (CON-61), whatever its adapter's row says: none of the user's settings, hooks, rules or servers, and never with `permissions = "skip"`. It never runs under the program's own plan mode: the harness holds the mode, and decides what the program asks by CON-103's basics and its own plan rules, at once on entering and leaving. Every request beyond them goes to its master with the tool and its arguments, and the program waits: `mode__agent_answer`, which exists only in orchestration mode, answers once, always or deny. No answer in 30 minutes, or no master, is a deny. CON-69 and CON-70 hold for the user's own conversations. |
| **CON-109** | An agent of an orchestra is bound to a journal entry. `mode__agent_spawn` takes `task`, an open entry, and refuses without one. The agent's system prompt names it and it starts at once. When done, with evidence, it asks its master to close the entry; only the master closes an agent's task. On approval it asks to close its session, and the master calls `mode__agent_close`, which stays the master's at any time. |
| **CON-110** | While an agent of an orchestra lives, the harness reminds its master every 10 minutes to check on it, naming the agent, its task and whether it is running. It starts with the spawn and ends with the agent's session by itself. |
| **CON-111** | An agent of an orchestra's plan holds, before it is approved, a mind map of its strategy (decisions, work, the proofs it will produce) pointing at its task, and a flowchart of the logic of what it builds. `mode__plan_exit` refuses a slave's plan until both exist; whether they are true is its master's to read. |
| **CON-112** | Guaranteeing that its agents' work matches the specs is the orchestrator's duty. Before approving an agent's work it checks the change against the specifications and constraints that bear on it, not only against the agent's report. If the agent broke a spec, it does not close the entry and sends it back with `agent_send`, naming the rule and what breaks it. A spec that has to change goes by the user's word. |
| **CON-113** | Drawing never takes a session down. A card that cannot be drawn shows a line saying so, its error goes to a log file, and the window goes on; a whole frame's panic is caught the same way. An item may be 4000 rows tall; what is past that is said on screen, with how much. |
| **CON-114** | `mindmap_add` and `flowchart_add` refuse a node past the map's limit, naming it. The limit is the `map_max_nodes` setting, on the settings page, 200 by default and 0 for none. |
| **CON-115** | `invariant` and `principle` are journal flags like `specification` and `constraint`: marks, binding, checked against `docs/spec/invariants.md` and `docs/spec/principles.md` and in the prompt's binding entries. A category of those names sets the flag. |
| **CON-116** | A message from Telegram, a callback or another agent during a run goes into the queue of CON-83: shown above the composer with its source, reaching the model at the next boundary in order of arrival, once, or starting the next run. It stays data from outside, never the user's message, and Up does not take it back. |
